# Depviz Public Distribution, Gradle Plugin, And CLI Design

## Objective

Make Depviz easy to run in Maven and Gradle Java projects without requiring the application project to add Depviz as a dependency or edit its build files.

The target user flow is:

```bash
depviz open
```

The command should detect the build tool in the current directory, run the correct Depviz plugin through that build tool, generate the offline viewer, and open it in the browser for local developer inspection.

## Product Principles

- Depviz remains a local developer tool.
- The analyzed application must not add Depviz as a compile/runtime dependency.
- The CLI must not reimplement Maven or Gradle dependency resolution.
- Maven and Gradle adapters should use the real build tool context so profiles, settings, mirrors, authentication, repositories, proxies, multi-module/multi-project structure, and wrappers keep working.
- The visual model remains a graph, not a duplicated tree. Shared dependencies are represented as one package node with multiple incoming edges.
- CLI, Maven plugin, Gradle plugin, core, schema, and viewer use the same Depviz version for predictable debugging.

## Public Coordinates

Use public coordinates aligned with the GitHub identity:

```text
groupId: io.github.lucasgois1.depviz
java package root: io.github.lucasgois1.depviz
gradle plugin id: io.github.lucasgois1.depviz
```

Planned artifacts:

```text
io.github.lucasgois1.depviz:depviz-core
io.github.lucasgois1.depviz:depviz-maven-plugin
io.github.lucasgois1.depviz:depviz-gradle-plugin
io.github.lucasgois1.depviz:depviz-cli
```

The Maven CLI path should always use the full plugin coordinate:

```bash
mvn io.github.lucasgois1.depviz:depviz-maven-plugin:<version>:open
```

This avoids requiring users to configure Maven `pluginGroups`.

## Repository Architecture

Convert the current single Maven plugin project into a multi-module repository:

```text
depviz/
  pom.xml
  depviz-core/
  depviz-maven-plugin/
  depviz-gradle-plugin/
  depviz-cli/
  viewer/
```

### `depviz-core`

Owns build-tool-independent behavior:

- graph document model
- artifact coordinate model
- graph deduplication
- graph paths
- viewer configuration model
- diagnostics model
- version insight model and checks that can be reused by adapters
- Snyk model, parser, runner, enrichment, and diagnostics
- viewer output writer
- static viewer assets packaging contract

The core must not depend on Maven project classes or Gradle project classes.

### `depviz-maven-plugin`

Owns Maven-specific behavior:

- Mojo parameters
- Maven dependency graph extraction
- reactor aggregation
- Maven repository metadata access for version checks
- mapping Maven scopes and optional flags into the core model
- invoking the core writer
- opening the browser when configured

The Maven plugin should stay thin. It adapts Maven data to the core contract and delegates product behavior to `depviz-core`.

### `depviz-gradle-plugin`

Owns Gradle-specific behavior:

- plugin ID `io.github.lucasgois1.depviz`
- task `depvizOpen`
- optional extension `depviz { ... }`
- Gradle dependency graph extraction
- Gradle multi-project aggregation
- mapping Gradle configurations into the core model
- invoking the core writer
- opening the browser when configured

The plugin must work when applied through a temporary init script generated by the CLI, so users do not need to edit `build.gradle` or `settings.gradle`.

### `depviz-cli`

Owns the user-facing command:

```bash
depviz open
```

The CLI detects Maven or Gradle, translates CLI flags into Maven properties or Gradle properties/init script configuration, runs the selected build tool, streams output, and returns the build tool exit code.

The CLI does not parse dependency files, resolve dependency graphs, run Snyk directly, or write viewer output itself.

### `viewer`

The viewer remains the React/Vite/Sigma frontend. Its build output is packaged for use by the core/plugin runtime. The generated viewer must remain offline and load only local files.

## CLI Behavior

### Installation

Initial installation is via GitHub Releases and an install script:

```bash
curl -fsSL https://raw.githubusercontent.com/lucasgois1/depviz/main/install.sh | sh
```

The installer writes:

```text
~/.depviz/bin/depviz
~/.depviz/lib/depviz-cli.jar
```

The installer should print PATH instructions if `~/.depviz/bin` is not already on the user's PATH.

For the first implementation, the CLI is a Java fat jar plus shell launcher, not a native binary.

### Project Directory

By default, the CLI uses exactly the current directory.

It does not walk parent directories looking for a project. This avoids surprising behavior in monorepos and nested directories.

Users can explicitly select a project directory:

```bash
depviz open --project-dir /path/to/project
```

If no supported build file exists in the selected directory, the CLI fails with:

```text
No Maven or Gradle project found in the current directory.
Run depviz from a directory containing pom.xml, build.gradle, or settings.gradle.
```

When `--project-dir` is used, the message should reference the selected directory rather than the current directory.

### Build Tool Detection

Maven detection:

- `pom.xml`

Gradle detection:

- `settings.gradle`
- `settings.gradle.kts`
- `build.gradle`
- `build.gradle.kts`

If both Maven and Gradle are detected and the terminal is interactive, prompt:

```text
Depviz found both Maven and Gradle in this directory.

1. Maven (pom.xml)
2. Gradle (build.gradle / settings.gradle)
3. Cancel

Choose build tool:
```

If both are detected and the terminal is non-interactive, fail with:

```text
Both Maven and Gradle were detected. Re-run with --tool maven or --tool gradle.
```

The user can force the tool:

```bash
depviz open --tool maven
depviz open --tool gradle
```

### Browser Behavior

The CLI opens the generated viewer by default in interactive terminals.

In non-interactive terminals, it generates files and prints the path without opening a browser.

Flags:

```bash
depviz open --open
depviz open --no-browser
```

`--open` forces browser opening. `--no-browser` disables browser opening.

### CLI Flags

Supported MVP flags:

```bash
depviz open --scope runtime
depviz open --scope compile
depviz open --scope test
depviz open --scope all
depviz open --snyk
depviz open --no-snyk
depviz open --snyk-json snyk.json
depviz open --snyk-org my-org
depviz open --snyk-all-projects
depviz open --snyk-command /opt/bin/snyk
depviz open --output build/depviz
depviz open --layout force
depviz open --open
depviz open --no-browser
depviz open --tool maven
depviz open --tool gradle
depviz open --project-dir /path/to/project
```

No `.depviz.yml` project config file is part of the MVP. The goal is zero project file changes.

### Maven Invocation

The CLI prefers `./mvnw` when present and executable, then falls back to `mvn`.

Example generated command:

```bash
./mvnw io.github.lucasgois1.depviz:depviz-maven-plugin:<cli-version>:open \
  -Ddepviz.scope=runtime \
  -Ddepviz.open=true
```

Maven output defaults to:

```text
target/depviz
```

### Gradle Invocation

The CLI prefers `./gradlew` when present and executable, then falls back to `gradle`.

The CLI writes a temporary init script and invokes:

```bash
./gradlew --init-script <temporary-depviz-init.gradle> depvizOpen
```

The init script applies `io.github.lucasgois1.depviz` at the same version as the CLI and configures the task from CLI flags.

Gradle output defaults to:

```text
build/depviz
```

Users can override both Maven and Gradle output:

```bash
depviz open --output .depviz/output
```

## Gradle Plugin Behavior

The Gradle plugin provides task:

```bash
./gradlew depvizOpen
```

Optional extension:

```kotlin
depviz {
  scope.set("runtime")
  outputDirectory.set(layout.buildDirectory.dir("depviz"))
  open.set(true)
  snyk.set("auto")
}
```

The CLI path must not require users to add this extension or apply the plugin permanently.

### Gradle Scope Mapping

Default:

```text
runtime -> runtimeClasspath
```

Supported mappings:

```text
runtime -> runtimeClasspath
compile -> compileClasspath
test    -> testRuntimeClasspath
all     -> all relevant resolvable configurations
```

`all` is opt-in because it can be noisy and large.

### Gradle Multi-Project Behavior

Gradle multi-project builds are aggregated by default, matching Maven multi-module behavior.

The graph contains:

- one synthetic root
- one structural node per subproject
- deduplicated dependency package nodes
- edges from subprojects and dependencies to the dependencies they use

If several subprojects depend on the same package coordinate, all subprojects point to the same dependency node.

Potential later narrowing flags:

```bash
depviz open --project :api
depviz open --project :worker
```

These project-selection flags are not required for the first implementation.

### Gradle Data Fidelity

The MVP Gradle adapter should capture:

- group
- artifact/module name
- version
- configuration/scope source
- subproject owner
- dependency paths
- graph deduplication by coordinate

It should not over-promise Maven-equivalent optional/classifier/scope fidelity where Gradle does not expose matching semantics cleanly. Missing or approximate metadata should be explicit in the adapter and tests.

## Snyk Behavior

The CLI exposes Snyk flags directly:

```bash
depviz open --snyk
depviz open --no-snyk
depviz open --snyk-json snyk-report.json
depviz open --snyk-org my-org
depviz open --snyk-all-projects
depviz open --snyk-command /opt/bin/snyk
```

Maven maps these to existing properties:

```text
depviz.snyk
depviz.snykJson
depviz.snykOrg
depviz.snykAllProjects
depviz.snykCommand
```

Gradle maps them to equivalent task/extension properties.

The viewer remains offline. Snyk is contacted only during graph generation when CLI/plugin configuration enables it.

Snyk findings must not fail the Depviz generation goal. Operational Snyk failures should generate diagnostics and still produce the dependency graph when dependency extraction and output writing succeed.

## Versioning

Depviz uses one version across all modules:

```text
depviz-cli 0.2.0
depviz-core 0.2.0
depviz-maven-plugin 0.2.0
depviz-gradle-plugin 0.2.0
viewer/schema 0.2.0
```

The MVP CLI does not expose `--plugin-version`. A version override may be added later for advanced debugging, but the default product contract is a locked version set.

## Publication And Release

Primary distribution:

- GitHub repository: source, docs, issues, releases
- GitHub Releases: CLI jar, launcher, install script, checksums
- Maven Central: JVM artifacts
- Gradle Plugin Portal: Gradle plugin ID

Planned release assets:

```text
depviz-cli.jar
depviz
install.sh
checksums.txt
```

The first implementation should prepare build metadata, module structure, package names, local release artifacts, and documentation.

Actual remote publication to Maven Central, Gradle Plugin Portal, and GitHub Releases may remain a documented/manual step until credentials, signing, repository setup, and release automation are configured.

## Testing Strategy

Required verification:

- unit tests for `depviz-core`
- existing Maven plugin unit tests after extraction
- Maven Invoker tests for:
  - single-project Maven
  - multi-module Maven
  - Snyk JSON
  - disabled Snyk/update checks
- Gradle TestKit tests for:
  - single-project Gradle
  - multi-project Gradle
  - runtime/compile/test scope mappings
  - output directory defaults
  - applying via init script
- CLI tests for:
  - build tool detection
  - Maven/Gradle ambiguity in interactive and non-interactive modes
  - wrapper preference (`mvnw`/`gradlew`)
  - flag translation
  - `--project-dir`
  - `--open` and `--no-browser`
- smoke tests:
  - CLI against a Maven fixture
  - CLI against a Gradle fixture
  - CLI with Snyk JSON
  - local Snyk CLI smoke when available

Browser verification remains useful for major viewer changes, but this design primarily changes distribution and adapters.

## Error Handling

CLI errors should be short and actionable:

- no supported project in selected directory
- Maven and Gradle both detected in non-interactive mode
- requested build tool not found
- wrapper not executable and fallback unavailable
- unsupported scope
- build tool command exits non-zero
- generated viewer path not found after a nominally successful build

Plugin errors should preserve current behavior:

- invalid config fails fast
- dependency extraction failures fail the plugin
- browser opening failures do not fail generation
- Snyk operational failures become diagnostics
- version lookup failures become diagnostics

## Implementation Boundaries

In scope:

- public coordinate/package rename
- multi-module repository structure
- core extraction
- Maven plugin migration to the new core
- Gradle plugin MVP
- CLI wrapper MVP
- install script and local release artifacts
- docs for Maven, Gradle, CLI, and installation

Out of scope for the first implementation:

- native binary builds
- `.depviz.yml`
- automatic parent-directory project discovery
- Gradle project-selection flags such as `--project :api`
- remote release automation that requires credentials
- guaranteeing Maven-equivalent optional/classifier semantics for Gradle where Gradle metadata differs

## Success Criteria

The first implementation is successful when:

- `depviz open` works from a Maven project without changing that project's `pom.xml`.
- `depviz open` works from a Gradle project without changing that project's `build.gradle`.
- Maven and Gradle multi-module/multi-project builds produce aggregate graphs with shared dependencies deduplicated.
- CLI Snyk flags work for Maven and Gradle.
- Browser opening defaults are correct for interactive and non-interactive use.
- All modules use `io.github.lucasgois1.depviz` coordinates/packages.
- Generated viewers remain offline static artifacts.
- Full test suites and Maven/Gradle/CLI smoke fixtures pass locally.
